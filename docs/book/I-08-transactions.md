## Workspace coordination and rollback ownership

**D-TXN-1 — Provisional. K-TXN:** one Workspace coordinator owns explicit nesting, implicit-operation policy, enlisted file identities and outcome receipts. A Database or cursor does not independently resolve a Workspace transaction. Microsoft's DAO documentation describes Workspace-wide scope and inner commits that remain reversible through outer rollback.[^workspace]

Maintain explicit transaction frames and separate statement/edit frames. On first mutation in a rollback scope, retain the necessary prior image, allocation/reference changes and catalog state; avoid logging an unchanged page repeatedly within that scope. Successful child commit merges retained changes and rollback obligations into its parent, preserving the earliest image needed by an outer rollback. Child rollback restores the policy-selected scope and discards its changes, retaining obligations still required by surviving outer scopes. Frames are memory/spill structures, not independently durable savepoints or an own WAL. Ordinary uncommitted reads use the owning transaction's private view; other readers follow I-09's visibility policy.

Prefer current-level logical resolution as the documented nesting baseline; R-TXN-1/TXN-NEST selects exact scope and depth limits. II-08 separates `ScopeBefore` entries from accepted semantic/generated-value receipts and private page revisions. An inner merge preserves the earliest image required by its parent; failed statement restoration uses that statement's before-image rather than the outer transaction's. Database bindings and native file participants are distinct, including aliases to one file. TXN-VIEW/SUPPORT determine which operations enlist without deriving transaction visibility from a cursor's Transactions capability. A statement rollback boundary is not a user-visible BeginTrans level. Close events, including Workspace and clone closure, reach the coordinator. Public objects may remain referenced after their underlying resources close; their subsequent errors/state must match the surface contract.

For multiple databases, enlist by verified identity, reserve resources and acquire known participants in stable order where this does not change observable behavior. Late enlistment uses explicit conflict handling, never an internal latch held while waiting. Successful resolution publishes the required in-process views coherently; partial-failure publication follows the observed outcome policy. No cross-file durable atomicity is inferred from this coordination, and no two-phase-commit side format is introduced. The owned `ResolutionAttempt` retains a participant-specific effect vector through failure, an empty commit, reentry and result marshalling. Logical frame/view transitions are recorded alongside native effects; a late error cannot revive a resolved frame. Publication uses reserved metadata and deferred release outside latches. TXN-MULTI/CLOSE select the public continuations and which scopes remain usable.

## Statement failures are a separate policy

**Preferred provisional rule:** where `dbFailOnError` applies, retain statement undo so a failed action can reverse that statement's successful changes while preserving the enclosing transaction as required. QueryDef.Execute's documentation supports rollback; Database.Execute's option table contradicts its own remarks.[^execute] R-SQL-2/R-TXN-1 settle the flag × explicit-transaction × operation × failure-class matrix before this rule is generalized. Without the flag, do not assume universal statement atomicity. DDL, generated identities, counts and error collections participate in that same investigation.

Rollback restores the relevant private and already-persisted state through an explicit protocol; releasing buffers is sufficient only if no covered persistent effects occurred. TEMP exhaustion is especially discriminating: DAO documents commit after exhaustion as potentially preserving an indeterminate subset, while rollback has different behavior.[^workspace] An internal uncertain state must retain progress and admissible next operations until the boundary can report the evidenced result. Do not replace it with a reassuring rollback success or a novel public error convention.

## Preferred provisional write ordering

**D-WRITE-1 — Provisional.** Implement a dependency-ordered native persistence program under the initial exclusive lease. The first candidate retains uncommitted changes privately and publishes one prepared operation/outer commit at a time. It reuses the native file's page, usage-map, index and catalog structures; it introduces no WAL or authoritative side database. R-FMT-2 supplies the structure/reference rules, R-TXN-1 the logical resolution rules, and R-CRASH-1/2 select the final ordering, acknowledgement and repair behavior.

II-03 makes physical granularity explicit: prepare complete immutable phase images and encode them to stored bytes; provisionally issue complete-page initialization and phase transfers, with a span-capable interface from the start. R-FMT-2/R-CRASH-1 select any required bounded spans, intermediate rewrites and ordering; a 4096-byte request is never assumed atomic. Detach old native backing and preserve required reader/rollback/pending-load images before the first overwrite, rather than waiting for logical commit.

A native page may contain more than one structure or require repeated writes. The coordinator compiles the table into a per-operation dependency graph over actual page images; it does not sort page numbers or assume that each table row is one atomic write. Cycles or in-place updates without a safe candidate require an explicit intermediate image/native transition and fresh cut analysis. An intermediate third image is permissible only if its native crash class is supported; it does not become an extra accepted optional-undo image.

For Windows, the initial force-flush adapter calls `FlushFileBuffers` on the relevant writable database handle after the required writes. Any additional native auxiliary-file or ordering requirement must come from the measured protocol. Microsoft documents both the DAO distinction between ordinary and forced commit and the Win32 difference between buffering and explicit flushing; neither specifies ACE's complete page schedule.[^flush] Do not force every phase to disk merely to simplify the proof: that could change ordinary commit survival. Do not call a successful flush a guarantee beyond the declared filesystem/device fault model.

**Nested force and engine options.** Prefer propagating an inner `CommitTrans(dbForceOSFlush)` intent to its parent while keeping the child reversible; this is a provisional choice, tested by TXN-FLUSH against inner force followed by outer rollback, ordinary commit and forced commit. If ACE writes early, its persisted rollback program becomes required; if the force request is confined or ignored, change the intent policy. Capture effective engine options and their generation, with SetOption/Idle as explicit events. Old registry examples do not establish target-build defaults, and cache refresh is not a demonstrated durability barrier.[^options]

II-08 compiles build dependencies, settled-transfer dependencies and actual persistence dependencies separately. Its key-update, LV/map and stable-root examples retain every intermediate image; the coordinator's typed logical/publication/flush nodes need not always occur in the simple table's order. Cancellation hands the same attempt to a qualified continuation, and uncertain progress blocks only the affected dependency closure as the public policy requires.

## Native crash baseline and optional recovery

**D-UNDO-1 — Decided. K-CRASH:** ACE-, Access- or CalcDb-first reopening must meet the ACE crash-state and commit-survival rules, including `dbForceOSFlush`, without requiring CalcDb recovery first. An evidenced needs-repair result is reproduced, not hidden by automatically running CalcDb's later repair engine. A completed healthy write additionally meets I-15's T-COMPACT-1 acceptance protocol; that test does not demand that every interrupted ACE-equivalent state be healthy.

### Whole-database optional-undo eligibility

The optional undo record is sealed before its covered database writes. It records the database identity/incarnation, operation, rollback eligibility, record integrity, before and intended file lengths, and a manifest partitioning **every database page in the union of the before/intended extents** into covered pages C and uncovered pages U. Headers, allocation/usage maps, indexes and catalog pages are included; no database range is unchecked. U records each page's baseline fingerprint. C retains each complete before-image and the complete intended new image or its fingerprint, with page lengths and explicit ABSENT states for pages created or removed by the operation.

At recovery, acquire exclusion, verify the same file identity and the complete record, then read the entire current database. **Every uncovered page must be unchanged; every covered page must equal either its before-image or its intended new image. Otherwise discard the undo record before making any recovery write.** Compare full bytes where images are retained and recompute the recorded fingerprints from the full read elsewhere. The current file length, page presence and partial final-page length must match a recorded before or intended alternative consistent with those page checks. An unrecorded extent, intermediate length, torn/third page image, identity mismatch or corrupt record rejects the whole operation. A mix of complete before/new pages is permitted; a mixed image within one page is not.

This is the user's selected external-change check. It does not claim that equal bytes prove an absence of past external activity, and it requires no continuous history witness or USN journal. The check may conservatively reject CalcDb's own interrupted intermediate page image if it is neither recorded alternative. The native crash baseline then applies without private recovery.

An otherwise matching sidecar must never undo a commit that the native baseline requires to survive, whether or not the caller received success. Rollback eligibility must therefore be durably disarmed before submission of the first effect that can cross the earliest evidenced commit-survival frontier for that operation and declared fault model; waiting for that effect to complete or for the API to return is too late. Record creation, disarm failure, the native frontier, acknowledgement and interrupted disposal belong to the coordinator's outcome protocol. This must preserve ACE's ordinary and forced-flush survival classes, without silently forcing additional native database durability. If the frontier or sound eligibility/disarming cannot be established with those properties for an operation/backend, leave optional undo disabled there. Absence, rejection or interruption of optional recovery never weakens ACE-first safety; each recovery write cut must independently satisfy the native baseline.

The identity and whole-file predicate are identical in I-03. Native-state recognition runs independently of the optional record; a missing or discarded record leaves the same native opening policy. Physical rollback of already-persisted changes uses a qualified persistence program too. Merely releasing transaction frames is sufficient only when no covered database effects occurred.

**D-UNDO-2 — Provisional.** Prefer a bounded, immutable private record and one-shot optional restoration: finish the full audit, compile and reserve a qualified native rollback program, then durably disarm before the first recovery database write. Begin with single-file complete-before restoration profiles; native effects that must survive rollback disable that profile. A second crash uses the already required native baseline. A failed seal or retirement can leave a credible Armed record, so its owned retirement obligation must settle before later conflicting work. II-08 supplies the codec, state machine and failure paths; R-CRASH-2 confirms or changes this protocol without changing D-UNDO-1's predicate.

## Direction when complete ACE crash tracing is impossible

Complete external tracing remains the preferred R-CRASH-1 experiment. A trace with dropped events or an uncontrolled selected cut is inconclusive for that claim. W-PROBE first attempts it on a minimal row update and an allocation/index-changing fixture and records the actual observation boundary and coverage; lack of complete capture must not become an indefinite prerequisite for all writer work.

The writer continues under the same exclusive native architecture. Instrument every CalcDb write, flush and acknowledgement; explore every allowed persistence cut in its deterministic VFS using an explicit storage model. In parallel, interrupt ACE at externally bracketed public-operation/commit milestones, vary timing to widen coverage, and inspect the frozen database/lock/TEMP state through independent reopeners. Combine those observations with the native graph constraints from R-FMT-2 and R-CAT-1. Preserve uncertainty about ACE boundaries that cannot be observed.

Qualify an operation/environment case only to the extent that all its modeled CalcDb cuts fit established ACE survival/repair classes, including acknowledged ordinary and forced commits. Random ACE kills alone do not establish exhaustive write-point parity, and process kills do not establish power-loss behavior. Cases requiring an unknown native state or persistence dependency remain experimental or refuse that mutation; prioritize a reduced fixture or better observation method while other writer cases advance. The full writer remains project scope. No private undo, invented WAL, atomic file replacement or stronger universal atomicity claim fills an evidence gap.
