# I-08. Transactions, write ordering and crash recovery

Revision 2 · Stage 1, response 3 · 2026-11-12

## Workspace coordination and rollback ownership

**D-TXN-1 — recommended.** One Workspace coordinator owns explicit nesting, implicit-operation policy, enlisted file identities and outcome receipts. A Database or cursor does not independently resolve a Workspace transaction. Microsoft's DAO documentation describes Workspace-wide scope and inner commits that remain reversible through outer rollback.[^workspace]

Maintain explicit transaction frames and separate statement/edit frames. On first mutation in a rollback scope, retain the necessary prior image, allocation/reference changes and catalog state; avoid logging an unchanged page repeatedly within that scope. Successful child commit merges retained changes and rollback obligations into its parent, preserving the earliest image needed by an outer rollback. Child rollback restores the policy-selected scope and discards its changes, retaining obligations still required by surviving outer scopes. Frames are memory/spill structures, not independently durable savepoints or an own WAL. Ordinary uncommitted reads use the owning transaction's private view; other readers follow I-09's visibility policy.

Prefer current-level logical resolution as the documented nesting baseline; R-TXN-1 determines exact rollback scope, depth limits and exceptional transitions. A statement rollback boundary is not a user-visible BeginTrans level. Close events, including Workspace and clone closure, reach the coordinator. Public objects may remain referenced after their underlying resources close; their subsequent errors/state must match the surface contract.

For multiple databases, enlist by verified identity, reserve resources and acquire known participants in stable order where this does not change observable behavior. Late enlistment uses explicit conflict handling, never an internal latch held while waiting. Successful resolution publishes the required in-process views coherently; partial-failure publication follows the observed outcome policy. No cross-file durable atomicity is inferred from this coordination, and no two-phase-commit side format is introduced.

## Statement failures are a separate policy

**Preferred provisional rule:** where `dbFailOnError` applies, retain statement undo so a failed action can reverse that statement's successful changes while preserving the enclosing transaction as required. QueryDef.Execute's documentation supports rollback; Database.Execute's option table contradicts its own remarks.[^execute] R-SQL-2/R-TXN-1 settle the flag × explicit-transaction × operation × failure-class matrix before this rule is generalized. Without the flag, do not assume universal statement atomicity. DDL, generated identities, counts and error collections participate in that same investigation.

Rollback restores the relevant private and already-persisted state through an explicit protocol; releasing buffers is sufficient only if no covered persistent effects occurred. TEMP exhaustion is especially discriminating: DAO documents commit after exhaustion as potentially preserving an indeterminate subset, while rollback has different behavior.[^workspace] An internal uncertain state must retain progress and admissible next operations until the boundary can report the evidenced result. Do not replace it with a reassuring rollback success or a novel public error convention.

## Persistence is an ordered, evidenced program

**D-UNDO-1 is fixed by the user's approval:** ACE-, Access- or CalcDb-first reopening must meet the ACE crash-state and commit-survival rules, including `dbForceOSFlush`, without requiring CalcDb recovery first. I-03 defines optional undo eligibility; it cannot establish this baseline.

Each participant supplies a dependency-ordered mutation program over its actual format structures. Prefer private preparation, validation and the smallest publication interval that preserves observable behavior. Resource reservations precede writes. Actual data/map/index/catalog write order, repair marking, reuse timing and lock-file transitions remain selected by R-CRASH-1/2; no generic ordering recipe is asserted sufficient. Flush requests carry the public durability intent and use only demonstrated adapter capabilities. A completed API call does not by itself prove power-loss survival.

Recovery validates the native state through evidenced recognition rules. Reproduce ACE's accepted, rejected or needs-repair classes; ordinary opening does not silently invoke CalcDb's later repair engine. Optional private undo is disabled unless its full identity/fingerprint/history check succeeds under exclusion. Any external modification or uncertain witness discards it; interruption during its application must also satisfy the baseline.

## Research and acceptance

R-TXN-1 starts with two databases, nested A/B/C edits, inner commit/rollback, outer rollback and each Close trigger. Record results, remaining transaction usability, row/cursor/catalog state and files after every call. Outcomes select frame-resolution and visibility policy. Repeat failure classes at first/middle/last mutation with options varied; never infer all cases from one lock failure.

R-CRASH-1/2 then use the already specified complete external ACE write trace and independent ACE/Access/Compact & Repair/CalcDb reopening branches. Process death, power loss and storage faults remain separate. Initial evidence comes through W-PROBE before the production writer; every implemented persistence cut is replayed afterward. No observed class means an unresolved protocol, not permission to invent stronger guarantees.

Measure unique/repeated dirty-page writes, rollback-image/spill bytes, transaction metadata, synchronization and flush calls. Coalescing repeated writes can improve cost only where it preserves the required visibility and crash classes. Tests exercise actual coordinator/pager logic under injected effects, with separate structural conservation checks. All experiment outcomes remain unobserved on ACE 16.0.20527.20016 in this session.

### R-CRASH-1 — Write-point crashes, surviving commits and independent reopeners

**Question and decision.** For each principal mutation, which database, lock-file and recovery states can ACE leave when interrupted at every write boundary, and which commits survive ordinary commit versus `dbForceOSFlush`? This evidence constrains D-UNDO-1 and the writer's ordering, acknowledgement, flush and repair-marking protocol. Private recovery cannot establish the ACE-first guarantee.

**Dependencies and size.** R-TXN-1 supplies transaction semantics; W-PROBE supplies an independent native observation/failure harness, before W-05 exists. R-FMT-1/2 and preservation work supply meaningful page comparisons. Initial scope **L**, with storage/environment extensions separately estimated. Replay the accepted matrix against CalcDb after W-05; do not make the initial ACE evidence depend on the production CalcDb pager.

**Fixture matrix.** Start each run from a fresh immutable fixture with known rows, long values, indexes, allocation state and catalog objects. Exercise scalar row changes; variable-row growth/shrink and relocation; inserts/deletes; inline/overflow long-value creation, growth, replacement and deletion; indexed-key updates, duplicate keys and index splits/merges/root changes; AutoNumber allocation; allocation reuse, map-capacity transitions and file growth; table/index DDL, catalog/property mutations and saved QueryDef create/change/delete. Include implicit operations, explicit commit/rollback, nested transactions and Workspace transactions spanning multiple databases. Record the exact operation sequence, parameters, options, transaction depth, affected files and caller-visible acknowledgements. Cover ordinary commit and `dbForceOSFlush` explicitly; record error/return boundaries without presupposing which establish durability. Fix and record actual loaded engine identity and Access host build, x64 caller surface (DAO initially, ADO when available), Windows locale, database sort/options, file format, filesystem, storage/cache configuration and flush behavior. Relevant managed caller checks use .NET Framework 4.8-family and .NET 10 LTS.

**Interruption method.** Observe ACE as a black box through an external OS/filesystem/storage tracing and controlled interruption facility. CalcDb VFS hooks cannot instrument ACE. First validate trace coverage and the controller's ability to pause relevant requests. Enumerate every database, lock-file and relevant TEMP write, including cache-manager and paging activity attributable to the fixture, including offsets, lengths, ordering, submission/completion and flush events. Replay from the fixture, pausing and killing ACE immediately before and after each observed write boundary, with every write point in the controlled trace covered; include flush boundaries and operation/commit acknowledgements. Record concurrent outstanding requests and any writes completing after the kill. Re-enumerate divergent traces rather than assuming replay always emits the same requests. Missing events, dropped traces, uncontrolled races or inability to establish the selected boundary make that run **inconclusive**.

Keep three fault models distinct: process termination with the OS/cache still running; OS/power interruption that loses volatile state; and specified partial/torn/reordered/failed writes or flushes. Use a controlled machine/storage fault facility for the latter models, and state precisely what it simulates and which persistence guarantees it assumes. A process-kill result is not power-loss evidence. Record the capture timing and cache/persistence boundary so later background writes cannot silently change the claimed crash image.

**Evidence and reopen branches.** Before any opener runs, preserve the database set, lock files, relevant TEMP files, trace, external acknowledgement record and fault metadata. Preserve both file bytes and absence/existence information. Use identity-preserving VM/volume snapshots where identity or failure semantics require them; do not flush volatile state merely to capture a power-loss image. Create independent branches from this frozen state for ACE, Access, Compact & Repair, and CalcDb. No branch may inherit another branch's open, automatic repair or compaction. Record each opener's errors, repair requests/markers, readable rows and typed values, surviving commits, index/catalog consistency, and all subsequent database/lock-file changes. Compact & Repair is a separate mutating diagnostic branch; its success is not ordinary-open success.

**Comparison and outcomes.** Align ACE and CalcDb by operation, transaction state, caller-visible acknowledgements and established persistence/dependency milestones—not by the ordinal number of a write. Compare semantic survival and repair/error behavior, supported by page and lock evidence; byte identity is not a universal acceptance rule. If CalcDb leaves a worse state or different commit-survival behavior, revise its write/flush/marking protocol and block acceptance of that writer path. If the ACE reference is ambiguous, retain the case as unresolved and collect discriminating evidence. If builds differ, preserve both captures against the declared baseline and require an explicit compatibility decision before broadening it; never select whichever answer passes. The next step is the complete-trace probe and the smallest row-update/commit fixture, followed by the operation matrix.

### R-CRASH-2 — Exhaustion, uncertain completion and guarded optional undo

**Question and decision.** What does ACE expose when TEMP space, database growth, transaction bookkeeping or I/O fails, and can CalcDb preserve that behavior while offering a strictly optional CalcDb-first undo enhancement? This decides D-TXN-1 resource/error handling and D-UNDO-1 eligibility and disposal. Dependencies: R-TXN-1, R-CRASH-1's harness and failure taxonomy, exclusion/identity probes. Size **M** as additional cases reusing that harness.

**Cases and measurements.** At each applicable reservation, spill, extension, overwrite and commit/rollback milestone, inject exhaustion, short/failed writes and flush failures; separately interrupt before and after the failure/error acknowledgement. Include nested and multi-database Workspace operations and both commit-flush modes. Record the primary error and subsequent usable/rollback/commit state rather than choosing a generic error-precedence rule. Capture database, lock and TEMP state before reopening; use R-CRASH-1's independent ACE, Access, Compact & Repair and CalcDb branches. An interrupted or failed request can have persistent effects: classify uncertain outcomes explicitly instead of assuming cancellation or an error means nothing was written.

**Optional-undo guard.** Every private undo record identifies its database file and fingerprints the covered pages for the intended recovery state. Eligibility additionally requires trustworthy, conservative evidence that **no external modification occurred since** the recorded state, followed by suitable exclusion while validating and applying recovery. Covered-page equality alone is insufficient. Whole-file equality alone also cannot rule out change-and-restore history. Test the proposed history/change witness, including its restart persistence and gaps; unavailable, expired or ambiguous evidence means **discard, never apply**. OS locks disappearing at process death do not provide this witness. If a portable trustworthy witness cannot be established, disable this optional enhancement for that environment.

Test untouched eligible recovery; same-path replacement; changed covered pages; changed uncovered pages; growth/truncation; changed-and-restored history; stale/missing/truncated undo; competing openers; and witness discontinuities. Use identity-preserving environment snapshots where required; ordinary file copies with new identities must not accidentally qualify. Verify rejection causes no undo write to the database. Test exhaustion and interruption during undo creation, recovery and disposal; every recovery write cut must itself satisfy the ACE-first crash baseline. Compare eligible CalcDb-first recovery with the same crash state without private undo, while independently accepting ACE-first behavior. Missing or discarded undo cannot weaken that baseline. The next step is a concrete witness/exclusion protocol and an adversarial eligibility fixture; no robust witness means an explicit disabled outcome, not speculative recovery.
